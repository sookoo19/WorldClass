## 今日学んだ概念

### Carbonはミュータブル（可変）オブジェクト
- **何か**: `Carbon`インスタンスに対して`->startOfDay()`や`->addDay()`のようなメソッドを呼ぶと、**新しいインスタンスを返すのではなく、呼んだインスタンス自身の中身を書き換えて**返す。
- **なぜ必要か**: これを知らずに使い回すと、後続処理で「さっき設定したはずの日付が勝手に変わっている」というバグを生む。
- **例え**: 紙のメモに直接書き込むイメージ。コピーを取らずに元のメモへ「0時に書き換え」と上書きすると、元の予定表自体が壊れる。コピー（`copy()`）してから書き込めば原本は無事。

### `usort`のカスタム比較関数
- **何か**: PHP標準関数。配列をソートする基準を、自分で書いたクロージャ（第2引数）で決められる。
- **なぜ必要か**: 日付と時刻という2つのキーを持つ配列を「日付優先、同日なら時刻順」で並べたいとき、標準の`sort()`では並べ替えの基準を指定できない。
- **例え**: 図書館の本を「著者名だけ」でなく「著者名→出版年」の2段階で並べたいとき、司書に独自のルールを渡すようなもの。

### `flip()` + `isset()` はO(1)存在チェックの定番パターン
- **何か**: 配列の「値」を「キー」に変換（`flip`）してから`isset()`で調べると、値の探索が一瞬で終わる。
- **なぜ必要か**: `in_array()`は配列の先頭から順に見ていく（要素数に比例して遅くなる=O(n)）のに対し、`isset()`は配列のキーへ直接アクセスするので要素数に関係なく一定時間（O(1)）。今回のように「窓内の全日付 × 全予約」を毎回チェックする処理では速度差が効いてくる。

## 書いたコード

### ミュータビリティを踏まえた日付範囲コピー

```php
$bookedKeys = $partner->sessions()
    ->whereIn('status', self::BLOCKING_STATUSES)
    ->whereBetween('scheduled_at', [
        $startDate->copy()->startOfDay(),
        $endDate->copy()->endOfDay(),
    ])
    ->get()
    ->map(fn ($s) => $s->scheduled_at->setTimezone($tz)->format('Y-m-d_H:i'))
    ->flip()
    ->all();
```

**ポイント解説:**
- `$startDate->copy()->startOfDay()`: `copy()`を挟まず`$startDate->startOfDay()`と書くと、**元の`$startDate`自体が0時に書き換わってしまう**。`$startDate`はこの後`while ($current->lte($endDate))`のループ判定にも使い回される変数なので、ここで壊れると後続の全処理が狂う。
- 同じ理由で`$current = $startDate->copy();`（ループ用の作業変数）も複製してから使っている。

### 日付＋時刻の2段階ソート

```php
usort($slots, fn ($a, $b) => "{$a['date']}{$a['start_time']}" <=> "{$b['date']}{$b['start_time']}");
```

**ポイント解説:**
- `"{$a['date']}{$a['start_time']}"`: `'2026-06-08'`と`'10:00'`を連結して`'2026-06-0810:00'`という1本の文字列にする。
- なぜ連結だけで正しく並ぶか: 日付が`Y-m-d`（例: `2026-06-08`）、時刻が`H:i`（例: `10:00`）という**桁数固定・大きい桁から並ぶ形式**だから。この形式なら文字列としての辞書順比較がそのまま時系列順と一致する。
- `<=>`（宇宙船演算子）: 左が小さければ`-1`、等しければ`0`、大きければ`1`を返す。`usort`はこの符号を見て並び替える。
- なぜ必要だったか: 直前の`foreach ($schedules as $schedule)`が**スケジュール単位**でスロットを積むため、`$slots`は「月曜の全日程→水曜の全日程→...」という並びで、日付順になっていない。UI側が日付順一覧を期待するので、最後にまとめてソートする。

### 除外条件の複合判定

```php
if (! isset($blockedDates[$dateStr]) && ! isset($bookedKeys[$key])) {
    $slots[] = [...];
}
```

**ポイント解説:**
- `$dateStr`（日付だけ）と`$key`（日付_時刻）は粒度が違う変数。`$blockedDates`は「その日を丸ごと」ブロック、`$bookedKeys`は「その時刻だけ」を予約済みとして塞ぐ。
- `! A && ! B`＝「AでもBでもない」。ド・モルガンの法則で言えば`!(A || B)`と同じ意味だが、今回のコードは素直に「ブロックされてない、かつ、予約されてない」の順で読める書き方を選んでいる。

## なぜそう書くか（設計の理由）

- **`copy()`を徹底する理由**: Carbonのようなミュータブルな値を関数内で使い回すとき、「このインスタンスは後でまた使うか？」を意識しないと、遠く離れた行の副作用で不可解なバグが生まれる。`PHP`には`DateTimeImmutable`という不変版もあるが、Carbonは`DateTime`（可変）ベースなので、複数箇所で使い回す設計では`copy()`が必須の防御になる。
- **文字列連結でソートキーを作る理由**: 日付・時刻を別々の数値として比較する複雑なロジックを書かずに済む。ただし`Y-m-d`や`H:i`のような**桁揃い・大きい桁優先**のフォーマットでないと成立しない前提条件がある（例: `'2026-6-8'`のようにゼロ埋めなしだと`'2026-10-1'`より`'2026-6-8'`が後に来てしまい壊れる）。

## 躓きポイント深掘り

### 「なぜ`$startDate->startOfDay()`と直接書いてはいけないのか」
- **何に躓いたか**: `copy()`を挟む理由が最初わからなかった。
- **根本の仕組み**: PHPのオブジェクトは基本的に**参照渡し**（変数はオブジェクトへの「参照」を持つ）。加えてCarbonの`startOfDay()`等は**破壊的メソッド**（自分自身を書き換えて`$this`を返す）。この2つが組み合わさると、「関数の途中で使った変数が、後で使うときには違う値になっている」という事故が起きる。関数型言語的に言えば「副作用」の一種。
- **関連技術マップ**:
  - **参照渡し vs 値渡し**: PHPの配列は値渡し（コピーされる）だが、オブジェクトは参照渡し。この違いを知らないと今回のようなバグに気づきにくい。
  - **DateTimeImmutable**: PHP標準にある不変版の日時クラス。操作のたびに新しいインスタンスを返すので`copy()`が不要になるが、Carbonの多くのプロジェクトは可変版の`DateTime`拡張として使われている。
  - **イミュータビリティ（不変性）設計**: このプロジェクトでも[[2026-06-08_マイグレーション型とテスト環境変数デバッグ]]で扱ったUseCaseの`readonly` Input/Outputと同じ思想（「値が途中で変わらない」ことを設計で保証する）。
- **理解チェック**: `$a = $startDate; $a->addDay();`のあと、元の`$startDate`はどうなっているか？（答: `$a`と`$startDate`は同じCarbonオブジェクトを指しているため、`$startDate`も1日進んでしまっている）
