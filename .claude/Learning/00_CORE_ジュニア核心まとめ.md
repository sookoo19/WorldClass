## 1. 設計の背骨 ── クリーンアーキテクチャと依存性逆転

### 原則: 内側（ビジネスルール）は外側（DB・HTTP）を知ってはいけない
- **核心**: 依存の矢印は常に「外→内」。UseCase（業務手順）が `User::create()`（Eloquent＝インフラ）を直接呼ぶと矢印が逆流して原則が壊れる。
- **なぜ大事か**: DBやフレームワークを将来乗り換えても、ビジネスロジックを1行も変えずに済む。テストもDBなしで回せる。
- **道具立て（3点セット）**:
  - **Repository Interface**（Domain層の契約書）… 「保存できる」とだけ宣言、中身は書かない
  - **Eloquent実装**（Infrastructure層）… `implements` して実際のDB操作をここだけに閉じ込める
  - **DI バインディング**（AppServiceProvider）… 「Interfaceが要求されたらこの実装を渡す」と起動前に紐付け
- **覚え方**: UseCaseのコードに具象クラス名（`EloquentXxx`）が一切出てこない＝正しく分離できている証拠。
- → 詳細: [2026-06-08 マイグレーション型とテスト環境変数デバッグ](./2026-06-08_マイグレーション型とテスト環境変数デバッグ.md)（Repository Interface / DI / ValueObject / DTO）、[2026-06-09 TDD-UseCase-UnitTest](./2026-06-09_TDD-UseCase-UnitTest.md)

### 原則: 層をまたぐデータは「素のオブジェクト」に詰め替える（DTO）
- **核心**: Controller は `Request` から必要な値だけ抜き、`readonly` な Input オブジェクトに詰めて UseCase へ渡す。戻りも Output で包む。
- **なぜ大事か**: UseCase が Laravel の `Request` を知らずに済む。`readonly`（不変）にすると途中で値が書き換わらない安全が型で保証される。戻り値を Output で包むと、後から返す情報が増えても呼び出し側が壊れない。
- → 詳細: [2026-06-08](./2026-06-08_マイグレーション型とテスト環境変数デバッグ.md)（UseCaseとInput/Output）

### 原則: 「決まった選択肢」は ValueObject（enum）にする
- **核心**: `'family'` のような生文字列（マジックストリング）を直書きせず、PHP の backed enum にする。
- **なぜ大事か**: タイプミスが実行前に防げる・どこで使われているか正確に追える。DB の enum 制約（最後の砦）と PHP enum（書く瞬間の関門）は**役割が違う二重ガード**であり、DRY違反ではない。
- → 詳細: [2026-06-08](./2026-06-08_マイグレーション型とテスト環境変数デバッグ.md)（ValueObject）

### 原則: フレームワーク都合（表示ラベル・画面の見た目）を Domain に持ち込まない
- **核心**: 「依存は外→内」は実装の細部にも効く。例: 管理画面で enum を日本語表示したいとき、Domain の `PartnerStatus` に Filament の `HasLabel` を実装すると **Domain が Filament に依存**してしまう（矢印が逆流）。ラベルは**表示層（Filament 側）に明示配列で**持たせる。
- **見分け方**: 「これは*ビジネスのルール*か、*見た目/特定ツールの都合*か」を問う。後者は内側（Domain/UseCase）に置かない。
- **なぜ大事か**: 管理画面を別ツールに替えても、表示用に B2B 画面を足しても、Domain を一切触らずに済む。
- → 詳細: [2026-06-24 追記Task10/11](./2026-06-24_enum→string化とbacked-enum-cast.md)（HasLabelをDomainに入れず表示層でラベル化）

## 2. テスト戦略 ── 何を・どの粒度で守るか

### 原則: Unit と Feature は目的が違う。両方あって完成
- **Unit**: クラス1つのロジック検証。依存はモックで差し替え、**DBを使わない**（高速・安定）。「正しい引数でリポジトリを呼んだか」を見る。
- **Feature**: HTTP→Controller→UseCase→Repository→DB→レスポンスの**全経路**を実DBで検証。`RefreshDatabase` で毎回クリーンに。「繋いだら動くか」を見る。
- **核心**: Unit だけだと「部品は正しいが繋ぐと壊れる」を見逃す。Feature だけだと遅く・原因特定が難しい。
- → 詳細: [2026-06-09 TDD-UseCase-UnitTest](./2026-06-09_TDD-UseCase-UnitTest.md)（Unit vs Feature 戦略）

### 原則: TDD は Red → Green → Refactor
- 失敗するテストを先に書く（🔴）→ 通る最小コード（🟢）→ 通したまま整える（🔵）。テストが安全網になりデグレを即検知。
- **モックは「外部」を差し替える道具**: DB・メール送信など、検証したい対象の外側を偽物にして、対象のロジックだけを浮かび上がらせる。
- **Facade モック（応用）**: `DB::transaction` を入れると Unit が実DBに繋ぎに行って落ちる → `DB::shouldReceive('transaction')->andReturnUsing(fn($cb)=>$cb())` で「皮だけ剥がし、中身ロジックは本番どおり」走らせる。
- **既存コードへのテスト（characterization）**: 実装が先にある場合、happy path は**初回から緑が正常**（純粋なRedは出ない）。狙いは回帰の安全網。それでも「書く→実行して観察」は省かない。初回で**赤**なら配線バグの本物の発見。
- → 詳細: [2026-06-09](./2026-06-09_TDD-UseCase-UnitTest.md)、[2026-06-23 Inertia登録フォーム…（追記Task8.5）](./2026-06-23_Inertia登録フォームTSX化と周辺設定の罠.md)、[2026-06-24 追記Task9](./2026-06-24_enum→string化とbacked-enum-cast.md)（Feature/characterization）

### 原則: テストは「本数」でなく「検証された分岐の種類」で考える
- **共有ロジックは1回だけテスト、重複させない**: 複数の入口が**同一のルール/仕組み**（例: 両FormRequestに同じ `email unique`）を使うなら、片方で1回テストすれば担保される。両方に同じテストを書くのは冗長。
- **代わりに「未検証の固有ロジック」を突く**: その入口だけが持つルール（例: Partnerだけの `themes` 配列バリデーション）こそ穴になりやすい。happy path だけで満足せず、固有の分岐を狙ってテストを足す。
- **覚え方**: 「もう1本書くなら、まだ通っていない経路を通すものを書く」。
- → 詳細: [2026-06-24 追記Task9](./2026-06-24_enum→string化とbacked-enum-cast.md)（重複メールはMember1本／themes固有検証を追加）

## 3. 型と安全性 ── 間違いを「書けなくする」

### 原則: 型はバグを実行前に潰すための道具
- **三層ガードの発想**: 許容値の防御は層で分ける。①入口（FormRequest の `Rule::enum()`）②アプリ型（PHP enum / backed enum cast）③DB（enum=CHECK制約・unique・FK）。層ごとに別の砦を置く。
- **③（DBの最後の砦）は維持コストとのトレードオフ**: Laravel の `$table->enum()` は **Postgresでは `varchar+CHECK制約`**。状態が増えるたびに制約の作り直しマイグレーションが要る。**頻繁に状態が育つ列**（注文・セッションのstatus等）はあえて `string` 化し、防御を①②に寄せるのが保守的。**状態が安定した列**（種別マスタ等）は enum のままが安全。「全部enum/全部string」ではなく列ごとに判断。本番データが無いうちが変更最安。
- **数値の型を選ぶ**: 金額・評価は `decimal`（正確）。`float` は2進近似で誤差が出るので金額に使わない。負があり得ない件数は `unsignedInteger`。
- **casts() で型を取り戻す**: DBから来る値は文字列。`'email_verified_at' => 'datetime'`、`'password' => 'hashed'`、`'status' => PartnerStatus::class`（**backed enum cast**＝DB文字列⇄PHP enumを読み書きで自動変換）。enum cast は JSON化時に自動で `.value`（文字列）へ戻るのでフロントは壊れない。
- **⚠️ cast は「その列を文字列比較してる箇所」と必ずセットで確認**: 既に `match($x->role)` や `in_array($x->role, $roles, true)` のように**文字列で厳密比較**しているコードがある列を enum cast すると、比較が全て false 化し、分岐や認可が**エラーも出さず黙って壊れる**。cast するなら比較箇所も enum比較に直すか、その列は string のまま据え置く。
- **⚠️ cast列は「whereの引数」と「取得後の属性」で型が違う**: `Model::where('status', 'pending')` の引数は**生の文字列**（DB値と照合）。一方 `$model->status` は cast が効いて **enumオブジェクト** → 比較は `->value` で。同じ列でも文脈で型が変わる。
- → 詳細: [2026-06-08](./2026-06-08_マイグレーション型とテスト環境変数デバッグ.md)（decimal/unsigned/casts）、[2026-06-06 Laravelセッション…](./2026-06-06_Laravelセッション衝突回避とGit規約.md)（casts）、[2026-06-24 enum→string化とbacked-enum-cast](./2026-06-24_enum→string化とbacked-enum-cast.md)（CHECK制約のトレードオフ / cast / roleをcastしない理由）

### 原則: 静的解析が型を追えるよう「情報を渡す」のも仕事のうち
- **`Auth::user()` の戻り型はインターフェース**（`Authenticatable`）。具体的な `App\Models\User` のプロパティ/リレーションは見えない → `/** @var \App\Models\User $user */ $user = Auth::user();` で型を明示。
- **リレーションは戻り型を書く**: larastan は `partner(): HasOne` ＋ `@return HasOne<Partner, $this>` の**戻り型**を見て `$user->partner` という magic プロパティを生成する。戻り型が無いと「未定義プロパティ」と誤検知。型注釈は人間の補足ではなく、解析器への入力。
- **切り分け**: 注釈を足してエラーが**次の行に移った**＝その層は効いた、別の原因が残っている、と読む。1回で消えなくても「効いてない」と早合点しない。
- → 詳細: [2026-06-24 enum→string化とbacked-enum-cast](./2026-06-24_enum→string化とbacked-enum-cast.md)（phpstan: Auth::user()型 / larastanリレーション戻り型 / phar欠落はreinstall）

### 原則: TypeScript は一括変換せず漸進移行（allowJs）
- **核心**: `allowJs: true` で `.jsx` を残したまま、新規から `.tsx`。`strict` で厳格チェック。
- **落とし穴**: strict な `.tsx` から型なし `.jsx` 部品を import すると、TS が JSソースから型を**誤推論**して大量エラー（rest props が空 `{}` 推論など）。→ 使う部品を型付き `.tsx` 化すれば解消し、全ページで恩恵。
- **グローバルは型宣言が要る**: import せず使う `route()`（Ziggy注入）は TS が知らない → `global.d.ts` で `declare` して型だけ後付け（実体はビルド時に存在）。
- → 詳細: [2026-05-29 npm依存解決-TypeScript導入](./2026-05-29_npm依存解決-TypeScript導入.md)、[2026-06-23](./2026-06-23_Inertia登録フォームTSX化と周辺設定の罠.md)

## 4. データ整合性 ── 「半分だけ成功」を許さない

### 原則: 複数の書き込みはトランザクションで原子化する
- **核心**: 登録は users→members の2回INSERT。途中失敗で「users だけ残る孤児ユーザー」ができ、`unique:users` でそのメールが**再登録不能**になり詰む。`DB::transaction(fn)` で全部成功 or 全巻き戻し。
- **1:1 は DB でも担保**: `hasOne` の前提を `$table->unique('user_id')` でDB層からも保証。
- **FK は親子の連鎖を定義**: `foreignId('user_id')->constrained()->cascadeOnDelete()` で親削除時に子も自動削除。アプリの消し忘れによる不整合を防ぐ。
- **同時実行は lockForUpdate**: 「承認」二重クリック対策。**対象レコード自身**をトランザクション内で `lockForUpdate()->findOrFail()` し直す（関連テーブルだけロックしても無意味）。
- → 詳細: [2026-06-23 追記Task8.5](./2026-06-23_Inertia登録フォームTSX化と周辺設定の罠.md)（transaction/unique）、[2026-06-08](./2026-06-08_マイグレーション型とテスト環境変数デバッグ.md)（constrained/FK）、[2026-06-10 セキュリティレビュー観点](./2026-06-10_セキュリティレビュー観点.md)（lockForUpdate）

## 5. Docker と環境差 ── 「自分のPCでは動く」を無くす

### 原則: コンテナ間はサービス名で通信する。`127.0.0.1` は自分自身
- **核心**: `REDIS_HOST=redis` / `DB_HOST=db`（compose のサービス名＝コンテナ内DNS）。`127.0.0.1`/`localhost` はそのコンテナ自身を指すので別コンテナには届かず「Connection refused」。
- → 詳細: [2026-05-25 Docker-PHP-Nginx構成](./2026-05-25_Docker-PHP-Nginx構成.md)、[2026-06-06](./2026-06-06_Laravelセッション衝突回避とGit規約.md)（DB_HOST=db）

### 原則: ネイティブバイナリは OS/アーキ依存。install と build は同じ環境で
- **核心**: `rolldown` 等の `.node` バイナリは Linux用/macOS用が別物。host(mac)の node_modules が container(linux)に漏れると動かない。`npm install` も `npm run build` も**コンテナ内で揃える**。lockfile が別OSで生成されると optional 依存が欠ける（npm #4828）→ node_modules と lockfile を消して入れ直し。
- → 詳細: [2026-05-29](./2026-05-29_npm依存解決-TypeScript導入.md)、[2026-06-23](./2026-06-23_Inertia登録フォームTSX化と周辺設定の罠.md)

### 原則: 「起動した」と「使える」は違う（healthcheck）
- DB はプロセス起動後も接続受付まで数秒。`depends_on: condition: service_healthy` で本当に準備完了してからアプリを起動。
- → 詳細: [2026-05-25](./2026-05-25_Docker-PHP-Nginx構成.md)

### 原則: 環境変数には複数の「置き場所」があり、優先順位がある
- PHP には `$_SERVER` / `$_ENV` / `getenv()` の独立した置き場所があり、ライブラリごとに見る場所が違う。Laravel の `Env` は `$_SERVER` を最優先 → phpunit.xml で `<env>` だけ指定しても `$_SERVER` を書き換えないと効かない（`<server>` タグが必要）。設定変更が効かないときは `config:clear`。
- → 詳細: [2026-06-08](./2026-06-08_マイグレーション型とテスト環境変数デバッグ.md)（$_SERVER/$_ENV/419デバッグ）

### 原則: `env()` は config ファイルの中だけ。アプリ本体は `config()` 経由で読む
- **核心**: 鍵やURLなど環境ごとに変わる値は `.env`（実値）→ `config/*.php`（`env()` で受ける）→ アプリ本体（`config('services.stripe.secret')`）の3段で扱う。コントローラ等で `env('STRIPE_SECRET')` を**直接呼ばない**。
- **なぜ大事か**: 本番高速化のため `php artisan config:cache` を打つと、その後 `env()` は **null を返す**（.envを読まなくなる）。config 経由なら値はキャッシュに焼かれていて無事。env 直読みの箇所だけ「本番でだけ鍵が null」になり、発見しづらい。
- **セット運用**: 新しい env を足したら必ず `.env.example` にも**値なしキー名**を追記（`.env` はGit無視・実値、example は共有テンプレ）。
- → 詳細: [2026-06-25 Stripe設定とスロット管理マイグレーション](./2026-06-25_Stripe設定とスロット管理マイグレーション.md)（env→config→app / config:cache罠）

## 6. セキュリティの習慣 ── 安全側に倒す

- **死にルートを残さない**: コントローラのメソッドを分割・削除したら、ルートファイルも grep。放置すると本番で初めて500に気づく。
- **重い入口にレート制限**: 登録POST に `throttle:5,1`（1分5回）。bot の大量登録・負荷を防ぐ。
- **秘密はコードに書かずenv**: 初期管理者パスワード等をハードコードしない。未設定なら**動かす方ではなく止める**（弱いパスで動くより安全）。
- **公開範囲を絞る**: Nginx の root は `public/` だけ。`app/` `.env` を Web から触れさせない。app コンテナはポートを外に出さず nginx だけ公開。
- **汎用カラムを意味付きに流用しない**: 「評価提出順」を `updated_at`（何でも更新される）で判定しない。専用の `rated_at` を持つ。
- **CSRF/419**: POST はトークン検証必須。テスト環境は `APP_ENV=testing` で正しく無効化。
- → 詳細: [2026-06-10 セキュリティレビュー観点](./2026-06-10_セキュリティレビュー観点.md)、[2026-05-25](./2026-05-25_Docker-PHP-Nginx構成.md)（public root）

## 7. デバッグの作法 ── 推測でなく一次情報

- **エラーメッセージの1行目を起点に**: `Route [dashboard] not defined` のように、文言が直接の手がかり。
- **ローカルとCIの差で原因を絞る**: 「ローカルだけ失敗・CIは通る」＝環境差が原因、と切り分けられる（419問題はこれで特定）。
- **推測で1回外したら、ソースを読む**: `force=true` で直る想定が外れた → phpunit のソースを直接読み、`<env>` が `$_SERVER` を書き換えないことを確認してから対策。**一次情報（ソース）で確かめる**と再現性のある解決になる。
- **回帰テストを信じる**: 自分の変更と無関係なテストが急に赤 → 別の変更で前提（名前付きルート等）が消えていないか疑う。全体テストがこれを検知してくれる。
- **「フォームのコードか、周辺設定か」をまず分ける**: 画面が出ない時、コード本体でなく Redis/build/blade/ロケール等の**設定**が原因のことが多い。tsc が通っているなら型・ロジックは無実、と切り分ける。
- **ツールが出すエラー＝コードのエラーとは限らない（並列ワーカーを疑う）**: phpstan/jest 等は高速化のため**子プロセス（並列ワーカー）**に処理を分担する。ワーカー自身がメモリ/プロセス制約で死ぬと `Child process error (exit code 255)` のような**インフラ層のエラー**が表に出て、原因コードが一切見えない。`--debug`（並列オフ・1プロセス実行）で再走させると真の結果が見える＝「コード由来か環境由来か」を切り分けられる。恒久対策はワーカー数を絞る（`parallel: maximumNumberOfProcesses`）。
- → 詳細: [2026-06-08](./2026-06-08_マイグレーション型とテスト環境変数デバッグ.md)、[2026-06-23](./2026-06-23_Inertia登録フォームTSX化と周辺設定の罠.md)、[2026-06-25 追記Task3](./2026-06-25_Stripe設定とスロット管理マイグレーション.md)（phpstan並列ワーカー255を--debugで切り分け）

## 8. 開発プロセス ── 積み上げを支える習慣

- **Conventional Commits**: `type(scope): 説明`。`feat`/`fix`/`refactor`/`test`/`docs`/`perf`/`chore`。機能が増えない設定変更は `chore`。
- **CI は役割ごとにジョブを分ける**: test / 静的解析(Larastan) / コードスタイル(Pint) を独立ジョブに → どこで落ちたか一目・並列で速い。
- **静的解析の level はバランス**: Larastan level 5（null安全を含む中程度）。0〜4は緩すぎ、6〜10はフレームワーク由来の偽陽性が増える。自動生成コードは除外。
- **パッケージは対応バージョンを必ず確認**: Filament v3 は Laravel 13 非対応 → v4。「依存の連鎖」で1つ変えると他も動く（vite8→plugin-react v5）。

## ジュニアが特に陥りやすい罠（早見表）

- ビジネスロジックを Controller に直書き → テスト不能・再利用不能（→ §1 UseCase）
- Unit テストで実DBを使う → 遅い・本来インフラの責務まで巻き込む（→ §2）
- 生文字列の選択肢を直書き → タイプミスが実行時まで残る（→ §1 ValueObject / §3 型）
- 複数INSERTを素で書く → 途中失敗で孤児データ（→ §4 トランザクション）
- `REDIS_HOST=127.0.0.1` のままコンテナ運用 → Connection refused（→ §5）
- host と container で別々に npm → ネイティブバイナリ不一致（→ §5）
- ソース変更後に再ビルド忘れ → 画面に反映されない（build は瞬間を固める）（→ §7）
- メソッド削除でルートを残す → 死にルートで本番500（→ §6）
- 状態が育つ列を enum(CHECK)で固定 → 状態追加のたびに制約マイグレーション地獄（→ §3）
- 文字列比較してる列を enum cast → match/認可が黙って全false化（→ §3）
- 計画書の列名を鵜呑み → 実在しない列で作業。grep で実物確認してから着手（→ §7）
- Domain enum に画面用ラベル(`HasLabel`等)を実装 → Domainがフレームワークに依存し層が逆流（→ §1）
- 管理者パスワード等をコードに直書き/未設定でも動かす → 公開リポジトリで弱パスadmin事故。env必須＋未設定なら止める（→ §6）
- cast列に不正値を代入（末尾スペース等）→ 書込時に ValueError で即発覚（string列なら黙って保存され後で地味バグ。castが安全側に倒す）（→ §3）
- コントローラ等で `env()` を直接呼ぶ → `config:cache` 後に本番でだけ null 化。値は `config()` 経由で読む（→ §5）
- 新env追加で `.env.example` 更新忘れ → 他メンバーが鍵不足で動かない（→ §5）
- 静的解析の `Child process error 255` を見て自分のコードを疑い続ける → 実は並列ワーカーの死。`--debug` で切り分ける（→ §7）
