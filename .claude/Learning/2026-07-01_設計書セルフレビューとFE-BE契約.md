# 設計書セルフレビューと FE-BE 契約設計

**日付**: 2026-07-01
**会話の概要**: フロントエンド実装計画書（handoff 統合・TSX 化）を実装前にレビューし、改善点10個を選択式で1つずつ決定して設計書に反映した。コードを書く前に「設計書自体のバグ」を潰す回。

---

## 今日学んだ概念

### 設計書のセルフ整合性レビュー
- **何か**: 設計書の中で「自分で宣言した制約」と「自分で載せたコード例」を突き合わせ、矛盾を探すレビュー手法
- **なぜ必要か**: 設計書にもバグはある。実装前に見つければ修正コストはテキスト編集だけで済むが、実装後に気づくとコードの書き直しになる
- **例え**: 契約書の「第1条」と「別紙の具体例」が食い違っていないか照合する校閲作業。今日は3件見つかった:
  1. 「日時は Presenter で JST 整形（フロントで再計算しない）」と宣言 → なのに新規ページのコード例はフロントで `toLocaleString` していた
  2. 「`.tsx` を先に試し `.jsx` にフォールバックが安全」と注記 → なのにコード例は `.tsx` 固定だった
  3. 「`Sessions/*` は `OpenSessions/*` にリネーム」と宣言 → なのに `Pages/Sessions/Checklist.tsx` を新規作成していた

### silent fallback（静かなフォールバック）の罠
- **何か**: `function Index({ sessions = mockSessions })` のように、props が来なかったら既定値（mock）で動いてしまう作り
- **なぜ危険か**: BE が props 名を typo したり渡し忘れても**エラーにならず、本番ユーザーに偽データ（mock の6件）が表示される**。エラーで落ちるバグより、静かに間違った表示が出るバグの方が発見が遅れて怖い
- **例え**: 自販機が売り切れのとき「売り切れ」と表示せず、見本のサンプル缶をそのまま出してくるようなもの。買った人は気づけない

### プレビュー専用ページパターン
- **何か**: Page 本体の props は必須にして、mock は `IndexPreview.tsx` のような別ファイルから明示的に渡す方式
- **なぜ必要か**: ①BE の渡し忘れは即エラーで見える ②mock が code splitting により本体ページのチャンクに混ざらない ③接続完了時に「Preview ファイルとルートを消す」だけで撤去できる（消し忘れも grep で見つけやすい）

```tsx
// Index.tsx — 本体。props 必須
export default function Index({ sessions }: { sessions: SessionSummary[] }) { ... }

// IndexPreview.tsx — プレビュー専用（接続後に削除）
import Index from './Index';
import { mockSessions } from '@/data/mockSessions';
export default function IndexPreview() {
    return <Index sessions={mockSessions} />;
}
```

### 死に値を型に含めない
- **何か**: `SessionStatus = 'confirmed' | 'open' | 'needs1' | 'needs2'` のうち後ろ2つは mock 表示の都合だけの値で、Presenter（実データ）は絶対に返さない「死に値」だった
- **なぜ直すか**: 型は「実際に流れてくる値の契約」を表すべき。mock 都合の値が混ざると、読む人が「BE から needs1 が来るのか」と誤解する。表示バリエーション（あと n 組で成立）は status ではなく `groups` / `minGroups` の**データ値**で表現できた
- **例え**: メニューに「試食会限定メニュー」を常設メニューとして載せない。注文できると誤解される

### タイムゾーン表示を「仕様として」決める
- **何か**: `new Date(iso).toLocaleString('ja-JP')` は**閲覧者のブラウザのタイムゾーン**で表示する（'ja-JP' は言語・書式の指定であって、タイムゾーンの指定ではない）
- **今日の決定**: これをバグではなく仕様として採用した。海外パートナーが見る画面は現地時刻で表示されるのがむしろ正しい。ただし「意図的な例外」だと Global Constraints に明記した
- **教訓**: 同じ挙動でも「気づかずそうなっている」と「決めてそうしている」は別物。決めたら設計書に書く

## 書いたコード

### Presenter テストに「一番壊れやすい変換」の assert を追加

```php
// before: now()->addDays(14)->setTimezone('UTC')->setTime(1, 0) — 実行日で値が動く
'scheduled_at' => Carbon::parse('2026-07-18 01:00:00', 'UTC'), // JST 2026-07-18(土) 10:00

$this->assertSame('7/18', $out['date']);   // UTC 01:00 → JST で日付・曜日・時刻を固定検証
$this->assertSame('土', $out['dow']);
$this->assertSame('10:00', $out['time']);
```

**ポイント解説:**
- 元のテストはわざわざ「UTC 01:00 = JST 10:00」でデータを作りながら、**肝心の JST 変換結果を1つも assert していなかった**。テストデータの用意と検証がズレる典型例
- `now()` 依存をやめて固定日時にした理由: `date` / `dow` は実行日で値が変わり、`assertSame('7/18', ...)` のような**完全固定の検証**が書けないから。テストは決定的（いつ実行しても同じ結果）にする

### resolvePageComponent の配列フォールバック

```js
resolvePageComponent(
    [`./Pages/${name}.tsx`, `./Pages/${name}.jsx`],  // .tsx 優先 → 無ければ .jsx
    import.meta.glob('./Pages/**/*.{jsx,tsx}'),
),
```

**ポイント解説:**
- `resolvePageComponent` は第1引数に**配列**を渡せる。先頭から順に glob 内を探すので、新規 `.tsx` ページと Breeze 既存の `.jsx` 認証画面が共存できる
- `.tsx` 固定だと既存 `.jsx` ページが解決できず全滅する。「注記には書いてあるがコードに反映されていない」矛盾を修正した

## なぜそう書くか（設計の理由）

- **props 命名は camelCase に全ページ統一**: 1ページだけ DB 由来の snake_case（`scheduled_at`）だった。「FE 計画が契約の正」と謳うなら、DB の都合（snake_case）→ FE の慣習（camelCase）への**変換は BE（Controller/Presenter）側の責務**と契約に明記する。境界のどちらが翻訳するかを決めておくと、実装時に迷わない
- **「当面ページネーションなしの全件表示」と設計書に明記**: 実装しないこと自体は問題ではない。「考えた上で今はやらない」と「考えていない」を区別できるよう、**決めないことを決めて書く**。将来 `{ sessions, pagination }` へ拡張する方針だけ添えた
- **50% 還元計算は FE のまま残す判断もした**: すべての指摘を直すのが正解ではない。変更可能性が低い確定ルールなら、props 契約を増やさない方を優先する判断もある（選択式で「FE 計算のまま」を選択）

## 躓きポイント深掘り

### default props の mock が「本番で静かに偽データを出す」リスクに気づいていなかった

- **何に躓いたか**: 元の設計書は「props 未指定なら mock 表示」を利点として設計していた（mock→実データの切替がコード変更なしでできる、と）。レビューで初めて「渡し忘れ時に**エラーではなく偽データ表示**になる」裏面に気づいた
- **根本の仕組み**: JS のデフォルト引数は `undefined` のときに発動する。Inertia は Controller が渡さなかった props を `undefined` として Page に渡すので、BE の渡し忘れ・typo がデフォルト引数の発動条件と**区別できない**。型チェック（tsc）も「optional な props に既定値がある」ため通ってしまい、どの層でも検知されない
- **関連技術マップ**:
  - **fail-fast 原則**: 異常時は静かに継続せず早く大きく失敗させる思想。env 未設定なら止めるシーダー（§6 の教訓）と同根で、今回は「props 不足なら型エラー/実行時エラー」に倒した
  - **code splitting**: Vite はページごとに JS チャンクを分割する。mock を Preview ページだけが import する形にすると、本体チャンクに mock が含まれない（バンドル削減の仕組み）
  - **Inertia の props 受け渡し**: `Inertia::render('Component', [...])` の配列がそのまま Page コンポーネントの props になる。FE と BE の境界がこの1点なので、ここの契約（名前・形・必須性）が最重要
- **理解チェック**: 「props 未指定なら mock 表示」の設計は、なぜ tsc でも実行時でも検知できないバグの温床になるか？（答え: optional + 既定値により、BE の渡し忘れとプレビュー利用が型上も実行時も区別できないから）

### 指摘を「全部直す/直さない」ではなく1つずつ意思決定した

- **何に躓いたか**: レビュー指摘が10個並ぶと、どれを採用するか曖昧なまま「だいたい直して」になりがち。今回は選択式（各論点に推奨案+代替案）で1つずつ決めた
- **根本の仕組み**: レビュー指摘には「自己矛盾の修正（ほぼ必須）」と「設計トレードオフ（どちらも正解になりうる）」の2種類が混ざる。後者は推奨と逆の決定（例: 日時はローカル時刻でよい・50%計算は FE のまま）も普通に起こるので、**決定ログ**として残す価値がある
- **関連技術マップ**:
  - **ADR（Architecture Decision Record）**: 「何を・なぜそう決めたか」を残す軽量ドキュメント。今回の決定ログ表はその簡易版
  - **YAGNI**: 今回の「ページネーションは当面やらない」「ハンバーガーメニューは今は非表示」のような「必要になるまで作らない」判断の名前
- **理解チェック**: レビュー指摘のうち「推奨と逆を選んでも正解になりうる」のはどんな種類の指摘か？（答え: 設計トレードオフ型。自己矛盾・検証漏れ型は原則直す）
