# 全プラン横断学習 — 実装計画6本から抽出したBE/FE設計パターン

**日付**: 2026-07-01
**会話の概要**: `docs/superpowers/plans/` の全6プラン（Phase 1 基盤 / Phase 2 カタログ・予約・Stripe / Phase 2.5 オープンセッション / Phase 3 準備フロー / Phase 4 物資支援 / FEハンズオン）を通読し、ジュニアエンジニアが持ち帰るべき設計パターン・セキュリティ習慣・計画書の書き方を横断的に抽出した。

## 今日学んだ概念

### 1. 冪等性（idempotency）— 「2回実行しても結果が変わらない」を時刻駆動処理の必須条件にする

- **何か**: 同じ処理を何度実行しても、1回実行したのと同じ結果になる性質。Phase 2.5〜4 の全スケジュールジョブ（成立判定・催促・自動キャンセル・リマインド・評価依頼・プール積算）がこの性質を持つよう設計されている。
- **なぜ必要か**: Laravel Scheduler は**毎時**ジョブを走らせる。「締切ちょうどに1回だけ動く」設計にすると、サーバー停止・再起動・重複起動で「動かなかった」「2回動いた」が起きる。毎時走って「対象を絞り込む条件」自体が重複を防げば、何回走っても安全。
- **例え**: 郵便配達員が毎時間ポストを見回るが、「未配達フラグが立っている手紙」しか配らない。同じ手紙を2度配ることはないし、1回見逃しても次の見回りで配られる。
- **プラン内の3つの冪等化手法**:
  1. **専用の送信済みカラム**: `unready_reminded_at` / `reminded_at` / `rating_requested_at` / `rating_reminded_at`。送ったら記録し、`whereNull(...)` で二度目は対象外にする（Phase 3）。
  2. **状態遷移の一方向ガード**: プール積算は「ready→completed の一度きりの遷移」の中で呼ぶから二重積算しない（Phase 4 Task 3）。キャンセルJobは冒頭で `status === cancelled なら return`（Phase 2.5 Task 6）。
  3. **対象抽出条件からの自然な脱落**: 自動キャンセルJobは `status=confirmed` のみ対象 → キャンセル処理後は confirmed でなくなり、次回の実行で勝手に対象から外れる（Phase 3 Task 6）。
- **テストも冪等性を明示的に検証する**: どのJobテストにも「2回実行しても送信は1回」というケースがある（`Mail::assertQueued(..., 1)` を2回handleの後に）。

### 2. ステータス機械（state machine）— 状態遷移は「許可された一方向」だけにする

- **何か**: レコードの `status` が取りうる値と、許される遷移経路を固定する設計。Phase 4 の物資支援申請は `pending→approved→paid` / `pending→rejected` の2経路のみ。
- **なぜ必要か**: 「approved を再度 approve」「pending を paid」のような不正遷移は、**お金の二重減算・二重送金**に直結する。遷移前に現在ステータスを確認し、違ったら例外で止める。
- **プランでの実装形**: 専用のドメイン例外 `InvalidSupportRequestStateException(string $expected, string $actual)` — 「期待した状態」と「実際の状態」の両方をメッセージに含めるので、ログを見ただけで何が起きたかわかる。
- **セッションも同じ**: `draft→open→confirmed→ready→completed` / `→cancelled`。`MarkSessionReadyUseCase` は「confirmed 以外からは ready にできない」を最初に検証する（Phase 3 Task 3）。

### 3. クライアント不信の原則 — 金額と在庫はサーバーが決める・再検証する

- **何か**: フォームから送られてくる値（金額・スロット日時）は改ざん可能という前提で、サーバー側で決定・再検証する設計。
- **なぜ必要か**: HTMLフォームやJSの値はDevToolsで書き換え放題。「フロントで計算した合計金額」をそのままStripeに渡すと1円決済が作れてしまう。
- **プランでの実装形（Phase 2 Task 8）**:
  - 料金はサーバー側定数 `BASE_PRICES = [45 => 8000, 60 => 10000]` から算出。リクエストの金額は一切使わない。
  - スロットは `SlotService::isAvailable()` で**予約POST時に再検証**（スケジュール外日時・締切超過・ダブルブッキングを一括で遮断）。カタログ表示時に空きだった枠が、POST時にも空きとは限らない。
  - フロントにも同じ `BASE_PRICES` 定数があるが、それは**表示用**。真実はサーバー側にある。
- **公開情報も絞る**: `support_pool`（内部財務情報）はカタログAPIのpropsに**意図的に含めない**。テストで `->missing('partner.support_pool')` と「無いこと」を検証する — 「出さない」もテスト対象になる。

### 4. Webhook設計の3点セット — fail-closed・冪等・CSRF除外

- **何か**: Stripe からの非同期通知（決済完了）を受けるエンドポイントの定石（Phase 2 Task 10）。
- **fail-closed（安全側に倒して閉じる）**: 署名検証のsecretが未設定なら「検証スキップで通す」ではなく**500で処理を止める**。設定漏れで誰でも偽Webhookを投げられる状態を防ぐ。テスト用bypassは `app()->environment('testing')` 限定 — 本番で絶対に有効化されない条件にする。
- **冪等**: Stripeは同じイベントを複数回送ることがある。`status !== 'pending' なら return` で二重確定・メール二重送信を防ぐ。
- **CSRF除外**: 外部サービスからのPOSTはCSRFトークンを持てないので `validateCsrfTokens(except: ['stripe/webhook'])`。除外は**このルートだけ**に絞る（全体除外は厳禁）。
- **どのレコードの話かは metadata で運ぶ**: Checkout作成時に `metadata: ['participant_id' => ...]` を仕込み、Webhookで読み戻す。URLパラメータではなくStripe側に保存されたデータなので改ざんされない。

### 5. 仮押さえ（draft/pending）のライフサイクル — 「押さえる・確定する・掃除する」の3点で完結させる

- **何か**: 決済前に枠を仮押さえする設計は、**必ず後始末とセット**で成立する。
- **プランでの全体像**:
  1. **押さえる**: 予約POSTで `sessions(draft)` + `participant(pending)` を作成 → SlotService の `BLOCKING_STATUSES` に draft を含めることで、決済中の枠も他人から見えなくする（超過販売防止）。
  2. **確定する**: Webhookで `pending→confirmed` / `draft→confirmed`。
  3. **掃除する**: (a) ユーザーがStripeでキャンセル → `cancel_url` の戻り先でpending削除・draft枠解放。(b) ブラウザを閉じて戻ってこない → `ExpirePendingApplicationsJob` が24時間経過したpendingを毎時掃除（24h = Stripe Checkoutの有効期限。それを過ぎたpendingは決済される可能性がゼロ）。
- **なぜ必要か**: 掃除がないと、離脱ユーザーのpendingが枠を永久に死蔵する。「作る処理」を書いたら「消えなかったらどうなる？」を必ず問う。

### 6. 同時実行制御 — lockForUpdate は「数える前」に「本体の行」へかける

- **何か**: 複数リクエストが同時に走ったときの競合を、DB行ロックで直列化する技法。
- **オープンセッション申込（Phase 2.5 Task 4）**: `DB::transaction` 内で**まず Session 行を `lockForUpdate()`**、その後に残枠カウント→participant作成。ロックせずに数えると、2人が同時に「残り1枠」を見て両方通ってしまう（超過販売）。ロックが後続リクエストを待たせるので、2人目は1人目のINSERT後の正確なカウントを見る。
- **支援申請の承認（Phase 4 Task 5）**: **申請行とパートナー行の両方**をロックし直してから状態確認・減算する。渡されてきたモデルインスタンスは古い可能性があるので、トランザクション内で `lockForUpdate()->findOrFail()` で**取り直す**のがポイント。
- **経験則**: 「読んでから書く」処理（カウント→INSERT、残高確認→減算）はすべて競合の候補。読みと書きをトランザクション+行ロックで1つの不可分な操作にする。

### 7. お金の計算規約 — 減算は負数ガード、比率は明文化、返金は参照IDで

- **負数ガード**: `decrement('support_pool', $amount)` に負数を渡すと**実質increment（残高増額）**になる。Filamentフォームの `minValue(1)` とUseCase内の `if ($amount < 1) throw` の**二重ガード**（UIは迂回できるのでサーバー側が本体）。
- **支援額の定義を1箇所に**: 「支援額 = **基本料金**の50%（ファシリテーターオプション分は対象外）」— `(int) floor($basePrice * 0.5)`。テストが `price_paid: 10500 / support_amount: 4000` で「オプションを足しても支援額は変わらない」ことを固定している。
- **申請時点では減算しない**: 支援申請（claimed）はプールを減らさず、**承認（approved）時に承認額だけ**減算。却下ならプール不変。「いつ・どのイベントで残高が動くか」を1つに絞ると突合しやすい。
- **返金は `stripe_payment_id`（PaymentIntent ID）**: 確定時に保存しておいたIDで `refunds->create()`。IDが無いparticipant（未決済）はスキップ。

### 8. 締切計算はモデルのヘルパーに一元化する

- **何か**: 「申込締切=3日前12時」「直前参加締切=12時間前」「準備完了期限=前日12時」を `Session::applicationDeadline()` / `lateJoinDeadline()` / `readyDeadline()` として**Sessionモデルに集約**（Phase 2.5 Task 2）。
- **なぜ必要か**: この締切は UseCase（申込検証）・Job（成立判定・催促・自動キャンセル）・質問送信の**5箇所以上**から参照される。各所で `subDays(3)->setTime(12,0)` を書き散らすと、仕様変更時に直し漏れが必ず出る。
- **副産物**: 「質問リストの締切は申込締切と同時刻」という仕様が `applicationDeadline()` の再利用でコードに表れる — 同じ値を使う理由がコードから読める。

### 9. ドメイン例外 — 業務ルール違反は専用例外クラスで表現する

- **何か**: `SessionFullException` / `ApplicationDeadlinePassedException` / `InsufficientSupportPoolException` など、`\DomainException` を継承した**業務ルール違反専用の例外**。コンストラクタでユーザー向けメッセージを内包する。
- **なぜ必要か**: Controller 側は `catch (SessionFullException|ApplicationDeadlinePassedException $e)` と**型で分岐**でき、`back()->withErrors(['apply' => $e->getMessage()])` とメッセージをそのまま画面へ流せる。「どんな失敗があり得るか」が例外クラスの一覧として見える。
- **層の観点**: 例外は `app/Domain/Exceptions/` に置く＝業務ルールの一部。HTTPステータス（403/422）への変換はController（外側）の仕事。

### 10. 計画書（implementation plan）自体の書き方 — 6プラン共通の骨格

- **1タスクの構造**: `Files（触るファイル一覧）→ Step（チェックボックス）→ Run（コマンド）→ Expected（期待結果）→ コミット（Conventional Commits のメッセージまで指定）`。「実行→期待結果」がペアなので、ズレた瞬間に気づける。
- **TDDが構造に埋め込まれている**: ほぼ全タスクが「Step 1: 失敗するテストを書く → Step 2: 失敗確認（Expected: FAIL）→ Step 3: 実装 → Step 4: PASS確認」。**FAILの確認自体がStep**になっているのが重要（正しい理由で落ちることの確認）。
- **セルフレビュー（スペックカバレッジ）**: 各プラン末尾に「仕様の要件 × 対応Task」の表。書き終えた計画を仕様と突き合わせ、漏れを実装前に発見する。Phase 2 はセキュリティ専用のチェック節まで持つ。
- **前提と改訂履歴**: 「Phase 2.5 完了が前提（`ProcessSessionCancellation` が存在すること）」のように**依存を明文化**。設計変更は「⚠️ 仕様変更（日付）」として本文にインライン記録（例: 物資支援がカタログ発送方式→領収書リインバース方式へ）。
- **所有境界（ownership boundary）**: FEハンズオン計画とphase計画の間で「ページ・Presenter は FE計画が所有 / Controller・route は phase計画が所有」を宣言し、各ページに「**BE接続契約**」（route名・controller@method・component名・props形）を置く。二重実装と契約ズレを構造で防ぐ。phase2.5 の旧Task 10 が「このTaskは実装しない・FE計画を参照」と**明示的に廃止**されているのは、境界変更の痕跡をプランに残す好例。

### 11. 先回りカラムと段階的リリース — Phase 1 のスキーマに Phase 2〜4 の席を用意する

- **何か**: Phase 1 のマイグレーションに `stripe_payment_id`（Phase 2で使用）・`ready_checked_at`（Phase 3）・`support_pool`（Phase 4）が最初から入っている。
- **なぜそうするか**: テーブル定義は後から変えるほど高い（データ移行・ダウンタイム）。**フロー（コード）は後から足せるが、データの形は先に決めておく**。逆に Phase 3/4 で本当に必要になった列（`meeting_url`・`rated_at`・`transfer_reference`）は、その時点の add マイグレーションで追加 — 全部を先回りするのではなく、**確度の高い骨格だけ**先に置く。
- **接続フックのコメント**: Phase 3 の `CompleteFinishedSessionsJob` に「`// Phase 4: ここで AccrueSupportPoolUseCase を呼ぶ`」というコメントが置かれ、Phase 4 Task 3 がそれを差し替える。フェーズ間の接続点をコードコメントで予約しておく手法。

### 12. ファイルの公開/非公開はストレージの選択で決まる

- **領収書（非公開）**: `store('receipts', 'local')` = private storage。Webから直接触れないパスに保存し、閲覧は `ReceiptController` 経由 — **本人パートナー or 管理者のみ** `abort_unless` で認可してから `Storage::response()` でストリーム返却（Phase 4 Task 6）。
- **活用写真（公開）**: `disk('public')` に保存し `<img>` で直接表示。ただし **jpg/png のみ許可** — SVG を許すと `<script>` を内包できるため公開ページでのXSSベクタになる（Phase 4 Task 8 の注記）。
- **判断基準**: 「そのファイルのURLを第三者が知ったら困るか？」→ 困るなら private + 認可ルート。公開するなら**実行可能性のない形式**に限定。

## プラン内の重要コードパターン（抜粋）

### 冪等な時刻駆動ジョブの型（Phase 3 RemindUnreadySessionsJob）

```php
$targets = Session::query()
    ->where('status', SessionStatus::Confirmed->value)  // ① 状態で絞る
    ->whereNull('unready_reminded_at')                   // ② 送信済みは除外（冪等の要）
    ->where('scheduled_at', '>', now())                  // ③ 過去分は対象外
    ->with('partner.user')                               // ④ N+1回避のeager load
    ->get()
    ->filter(fn (Session $s) => now()->greaterThanOrEqualTo($s->applicationDeadline())); // ⑤ 締切超過のみ

foreach ($targets as $session) {
    Mail::to($session->partner->user->email)->queue(new PartnerPrepReminder($session));
    $session->update(['unready_reminded_at' => now()]);  // ⑥ 送ったら即記録
}
```

**ポイント解説:**
- `whereNull('unready_reminded_at')`: この1行が冪等性の本体。毎時実行でも送信済みには二度と送らない
- `->filter(fn ...)`: 締切計算はSQL化しづらいのでコレクション側で。件数が多くなければ十分
- `queue(...)`: 同期送信でなくキュー投入。メールサーバーが遅くてもジョブ全体が詰まらない
- `Mail::to(null)` ガード: 管理者宛先が未設定のときは例外でなく `logger()->warning` でスキップ — 通知の欠落でジョブ全体を殺さない

### 行ロックで残枠検証を直列化（Phase 2.5 ApplyToOpenSessionUseCase）

```php
public function execute(ApplyToOpenSessionInput $input): SessionParticipant
{
    return DB::transaction(function () use ($input) {
        // 行ロック: 並行する申込はここで直列化され、残枠カウントが正確になる
        Session::query()->whereKey($input->sessionId)->lockForUpdate()->first();

        $session = $this->validateApplication($input);  // 締切・満枠チェック

        return SessionParticipant::create([...]);
    });
}
```

**ポイント解説:**
- ロック→検証→作成の順序が本質。検証を先にやってからロックしても手遅れ（検証時点の情報が古い）
- `validateApplication` は public に分離されていて**Unitテストはロックなしで検証部分だけ**をモックリポジトリで試験できる。トランザクション込みの動きはFeatureテストが担う — テスト容易性のためのメソッド分割

### fail-closed な Webhook 署名検証（Phase 2 WebhookController）

```php
if (app()->environment('testing') && $sigHeader === 'bypass') {
    $event = json_decode($payload, true);  // テスト環境のみ検証スキップ
} else {
    // fail-closed: secret未設定なら処理しない（設定漏れで検証が無効化されるのを防ぐ）
    abort_if(empty($secret), 500, 'Stripe webhook secret is not configured.');

    try {
        $event = Webhook::constructEvent($payload, $sigHeader, $secret);
    } catch (SignatureVerificationException) {
        return response('Invalid signature', 400);
    }
}
```

**ポイント解説:**
- bypass条件は「testing環境 **かつ** 特定ヘッダ」のAND。どちらか片方では動かない
- secret未設定は「攻撃」ではなく「設定ミス」なので500（サーバー側の問題）、署名不一致は400（リクエスト側の問題）— ステータスコードで原因の所在を区別

### 二重ロックでお金の状態遷移を守る（Phase 4 ApproveSupportRequestUseCase）

```php
DB::transaction(function () use ($request, $approvedAmountJpy) {
    // 申請行・パートナー行の両方をロック:
    // 同一申請の二重承認（プール二重減算・二重送金）と残高の同時更新を防ぐ
    $lockedRequest = SupportRequest::lockForUpdate()->findOrFail($request->id);
    $partner = Partner::lockForUpdate()->findOrFail($lockedRequest->partner_id);

    if ($lockedRequest->status !== SupportRequestStatus::Pending->value) {
        throw new InvalidSupportRequestStateException('pending', $lockedRequest->status);
    }
    if ($approvedAmountJpy > $partner->support_pool) {
        throw new InsufficientSupportPoolException();
    }

    $partner->decrement('support_pool', $approvedAmountJpy);
    $lockedRequest->update([...]);
});

Mail::to(...)->queue(...);  // メールはトランザクションの外で
```

**ポイント解説:**
- 引数で受けた `$request` を使わず `findOrFail($request->id)` で**取り直す** — ロック付きの最新状態で判定する
- ステータス確認は**ロック取得後**。ロック前に見た pending は、待っている間に別リクエストが approved に変えたかもしれない
- メール送信はトランザクション外。トランザクション内で外部I/Oをすると、ロック保持時間が伸びる＆送信後にロールバックすると「送ったのに無かったことになる」

## なぜそう書くか（プラン全体を貫く設計判断）

- **「毎時実行＋条件絞り込み」を「締切ぴったりに1回実行」より優先する**: 正確なスケジュール実行は魅力的に見えるが、失敗時のリカバリがない。毎時＋冪等なら、1回スキップしても次で追いつく。**時刻の正確さより回復可能性**。
- **participant単位の決済に統一（Phase 2 の中核判断）**: 専用セッションもオープンセッションも「`session_participants` 1行 = 1決済」。Checkout作成・Webhook確定・返金がすべてparticipant単位の同じコードで済み、Phase 2.5/3 が `StripeService`・`ProcessSessionCancellation` を**そのまま流用**できた。抽象の単位を早期に正しく選ぶと、後続フェーズの実装量が激減する。
- **キャンセル処理を汎用Jobにした（Phase 2.5 → 3 で流用）**: `ProcessSessionCancellation(Session, string $reason)` は「不成立キャンセル」「準備未完了キャンセル」「運営手動キャンセル」の3つの入口から呼ばれる。**理由を引数にして処理を1本化**し、返金・クーポン発行・メール・ステータス更新の整合を1箇所で守る。
- **UIの二重ガードはサーバーが本体**: Filamentの `minValue(1)`・`visible(fn...)` は利便性のため。本当の防御はUseCase内の例外。「UIで制限したから大丈夫」は禁句（UIは常に迂回可能）。
- **Presenterでの日本語変換・JST整形はBE責務（FE計画）**: `culture→文化交流`・`Kenya→ケニア`・UTC→JST の変換をフロントに散らばらせず `SessionViewPresenter` に集約し、**Presenterを直接テスト**して形を固定。フロントは受け取った文字列を表示するだけ — 変換ロジックの単一情報源。
