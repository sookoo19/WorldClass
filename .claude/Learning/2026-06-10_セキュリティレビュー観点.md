## 今日学んだ概念

### 死にルート（dead route）
- **何か**: ルーティング定義は残っているが、呼び出し先のコントローラメソッドが既に削除・分割されているルート
- **なぜ必要か**: これを知らずに放置すると、誰かがそのURLにアクセスした瞬間に「メソッドが存在しない」というエラー（500エラー）が発生する
- **例え**: 引っ越した友達の旧住所宛に手紙を送り続けるようなもの。手紙（リクエスト）は届いても、受け取る人（メソッド）がもういない

今回の例: `routes/auth.php` に `Route::post('register', [RegisteredUserController::class, 'store'])` が残っていたが、`store()` は `storeMember()` / `storePartner()` に分割されて既に存在しなかった。

### throttle（レート制限）
- **何か**: 同じ人・同じIPから一定時間内にできるリクエスト回数を制限する仕組み
- **なぜ必要か**: 制限がないと、ボットが登録フォームに何百回も自動送信して、大量の不正アカウントを作ったり、サーバーに負荷をかけたりできてしまう
- **例え**: 窓口で「1人1回5分待ってください」というルールを設けるイメージ。何度も並び直されると窓口がパンクする

今回の例: 会員登録・パートナー登録のPOSTに `throttle:5,1`（1分間に5回まで）を追加する方針をプランに追加した。

### 環境変数によるパスワード管理（env必須化）
- **何か**: パスワードのような秘密情報をコードに直接書かず、`.env` ファイルや環境変数から読み込む方式
- **なぜ必要か**: コードに直接書く（ハードコードする）と、Gitリポジトリに「初期管理者パスワードは admin123456」という情報がそのまま残ってしまい、誰でも見られる
- **例え**: 家の鍵の番号を玄関のドアに貼り紙して書いておくようなもの。リポジトリ＝玄関ドアは多くの人（チームメンバーやGitHub上の閲覧者）が見られる場所

今回の例: AdminUserSeederが `admin123456` という固定パスワードで管理者アカウントを作る設計だったため、`ADMIN_SEED_PASSWORD` という環境変数を必須にし、未設定なら作成自体をスキップして警告を出す方式に変更した。

### updated_at を「特定イベントの順序」に使う危うさ
- **何か**: `updated_at` はLaravelがレコードのどんな変更でも自動更新する汎用カラム。特定の操作（例: 評価を提出した順番）の記録には向かない
- **なぜ必要か**: 「直近3回連続で低評価だったらアカウントを非表示にする」というロジックを `updated_at` の新しい順で判定すると、評価とは無関係な更新（リマインドメール送信時のフラグ更新など）でも `updated_at` が変わってしまい、本来の評価提出順とズレてしまう
- **例え**: 図書館で「最後に借りた人」を知りたいのに、「最後にこの本に触れた人」（返却作業した職員も含む）の記録を見てしまうようなもの

今回の例: `session_participants` テーブルに専用カラム `rated_at`（評価提出時刻）を新設し、そちらでソートするようにプランを修正した。

### lockForUpdate と二重実行レース
- **何か**: `lockForUpdate()` は、トランザクション内でそのレコードに「他の処理が同時に触れないように」ロックをかけるLaravelの仕組み
- **なぜ必要か**: 「承認」ボタンを同時に2回押された場合（二重クリック・多重リクエスト）に、同じ申請が2回承認されて二重に送金記録が作られてしまう、といった事故を防ぐ
- **例え**: ATMで同時に2回「引き出し」ボタンを押しても、片方の処理が終わるまでもう片方は待たされる、という仕組みに近い

今回の例: `ApproveSupportRequestUseCase` で、関連する `partners` テーブルだけをロックしていて、肝心の `support_requests`（承認対象そのもの）はトランザクション開始前の古い状態のまま使っていた。これだと2つのリクエストが両方とも「まだ承認されていない」という古い情報を見て処理を進めてしまう。修正として、トランザクション内で `SupportRequest::lockForUpdate()->findOrFail($id)` により対象レコードを取得し直すようにした。

### enumフィクスチャとDB制約の不一致
- **何か**: テストデータ（fixture）に書く値が、実際のDBマイグレーションで定義された `enum(...)` の許可値と一致していないと、INSERT時にエラーになる
- **なぜ必要か**: マイグレーション（DB側の定義）とテストコード（プラン側の記述）は別々に書かれることが多く、後から定義を変更すると食い違いが発生しやすい
- **例え**: 受付フォームの選択肢が「A・B・C」しかないのに、申込書のサンプルに「D」と書いてしまっているようなもの。実際に提出すると弾かれる

今回の例: 複数の実装プランで `'provider_type' => 'school'` と書いていたが、実際のマイグレーションでは `enum('overseas_school', 'local_japanese')` のみ許可されており、`'school'` は無効値だった。全箇所を `'overseas_school'` に修正した。

## 書いたコード

今回はコードではなく、実装プラン（Markdownの設計書）の修正のみ。代表的な修正方針の一例:

```php
// Before（プラン内の旧記述イメージ）
'provider_type' => 'school',

// After
'provider_type' => 'overseas_school',
```

```php
// ApproveSupportRequestUseCase の修正イメージ
DB::transaction(function () use ($id, $approvedAmountJpy) {
    if ($approvedAmountJpy < 1) {
        throw new \DomainException('承認額は1円以上である必要があります');
    }

    // トランザクション内で対象レコードをロック付きで再取得
    $supportRequest = SupportRequest::lockForUpdate()->findOrFail($id);
    $partner = Partner::lockForUpdate()->findOrFail($supportRequest->partner_id);

    // ここから先で承認処理・support_pool減算
});
```

**ポイント解説:**
- `lockForUpdate()->findOrFail($id)`: トランザクション開始後にロック付きで取得し直すことで、「承認済みかどうか」の最新状態を見て判定できる
- `if ($approvedAmountJpy < 1)`: 承認額が0円以下の不正な値を弾くガード

## なぜそう書くか（設計の理由）

- **死にルートを残さない**: コントローラのメソッドを分割・削除したら、必ず対応するルートファイルもgrepで確認する習慣をつける。リンク切れと同じで、放置すると本番で初めて気づくことが多い
- **パスワードはenv必須化**: 「動かなくなる（スキップされる）」方が「弱いパスワードで動いてしまう」より安全、という判断。安全側に倒す設計
- **専用タイムスタンプカラムの新設**: 既存カラム（updated_at）の「ついで利用」は将来の機能追加で必ず壊れる。意味が違うものは別カラムにする
- **lockForUpdateは「対象そのもの」にかける**: 関連レコードだけロックしても意味がない。承認・更新の主役となるレコード自身を再取得＋ロックする
