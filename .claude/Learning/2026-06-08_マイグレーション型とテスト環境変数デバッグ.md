# マイグレーションのカラム型とテスト環境変数デバッグ

**日付**: 2026-06-08
**会話の概要**: Phase 1のmembers/partnersテーブルを実装しながらマイグレーションのカラム型を学び、その後ローカルでだけテストが419エラーで落ちる問題を根本原因まで突き止めて修正した。

---

## 今日学んだ概念

### `constrained()` と外部キー制約
- **何か**: マイグレーションで「このカラムは別テーブルのidを参照する」という制約（外部キー制約）を1行で書けるメソッド
- **なぜ必要か**: 親テーブル（例: `users`）のレコードが消えたとき、子テーブル（例: `members`）の関連レコードをどう扱うかをDBレベルで保証するため。アプリ側のコードで消し忘れる、というデータ不整合を防げる
- **例え**: 図書館で「この本カードには持ち主の会員番号が必須」というルールをカード自体に刻み込んでおくイメージ。会員が退会したら、そのカードも自動で処分される設定（`cascadeOnDelete()`）にできる

```php
$table->foreignId('user_id')->constrained()->cascadeOnDelete();
```
- `foreignId('user_id')`: `user_id`という符号なし整数カラムを作る
- `constrained()`: カラム名（`user_id`）から参照先テーブル（`users`）と参照先カラム（`id`）を自動推測してFK制約をつける
- `cascadeOnDelete()`: 親（`users`）のレコードが削除されたら、子（`members`）のレコードも連鎖的に削除する

### `decimal` 型と `float` の違い
- **何か**: 小数を正確に保存するための列型。`decimal('rating_score', 3, 2)`なら「全体3桁・小数点以下2桁」＝`0.00`〜`9.99`の範囲
- **なぜ必要か**: `float`（浮動小数点）は2進数で近似するため`0.1 + 0.2`が`0.3`にならないような誤差が出る。評価スコアや金額など「正確さ」が重要な値には不向き
- **例え**: `float`は「だいたいこのくらい」というアバウトな目分量、`decimal`は「定規で測った正確な数値」。★評価の平均（4.25など）はdecimalで正確に持つべき

**ポイント**: PHPで取得すると文字列で返るため、Eloquentモデル側で `'rating_score' => 'float'` とキャストして数値として扱えるようにしている

### `unsignedInteger` 型
- **何か**: 0以上の整数だけを許す列型
- **なぜ必要か**: `penalty_count`（ペナルティ件数）や`support_pool`（支援プール残高）のように、論理的に負の値があり得ない項目に使うことで、不正な値をDB層で防ぎつつ、正の値の上限を約2倍に広げられる（符号ビットを正の数に回せるため）
- **例え**: 「マイナスの個数」はあり得ない、という現実のルールをDBの型で表現する

### CSRFトークンと419エラー
- **何か**: `419 Page Expired`は、フォーム送信時のCSRF（Cross-Site Request Forgery、なりすましリクエスト）トークンの検証に失敗したときにLaravelが返すエラー
- **なぜ必要か**: 悪意あるサイトから自分のサイトへ偽のフォーム送信をされる攻撃を防ぐため。Laravelは標準でPOSTリクエストにトークン検証を要求する
- **例え**: 窓口で「整理券」を持っていない人の申請は受け付けない、というルール。テスト環境では「テスト用窓口だから整理券チェックを省略していいよ」という設定（`APP_ENV=testing`）が必要

### `$_SERVER` と `$_ENV` と `getenv()` の違い（環境変数の3つの置き場所）
- **何か**: PHPで環境変数を保持する仕組みは複数あり、それぞれ独立した「置き場所」を持つ
  - `$_SERVER`: Webサーバー/PHP起動時にOSから渡されるスーパーグローバル変数
  - `$_ENV`: 同じく起動時にセットされるが、別の置き場所
  - `getenv()`/`putenv()`: OSの環境変数テーブルを読み書きする関数
- **なぜ必要か**: ライブラリやフレームワークによって「どこを優先して読むか」が違うため、設定が反映されない不可解なバグの原因になりうる。今回はまさにこれが原因だった
- **例え**: 同じ「住所」という情報が、住民票・運転免許証・会社の登録情報の3箇所に別々に記録されているようなもの。更新するときにどれか1つだけ書き換えても、別の場所を参照しているシステムには反映されない

---

## 書いたコード

### マイグレーション: members テーブル

```php
Schema::create('members', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->enum('type', ['family', 'cram_school', 'circle', 'public_facility', 'other']);
    $table->string('org_name')->nullable(); // 家庭はnull
    $table->string('prefecture');
    $table->string('contact_name');
    $table->string('grade_range')->nullable();
    $table->timestamps();
});
```

**ポイント解説:**
- `enum('type', [...])`: あらかじめ決まった選択肢の中から1つを選ぶカラム（利用者区分）
- `->nullable()`: `org_name`（法人名）は家庭利用者なら存在しないため、空（NULL）を許可する
- `grade_range`は「家庭利用者の場合はお子さんの学年帯」を表す

### モデル: Member（Laravel 13の属性スタイル）

```php
#[Fillable(['user_id', 'type', 'org_name', 'prefecture', 'contact_name', 'grade_range'])]
class Member extends Model
{
    public function user()
    {
        return $this->belongsTo(User::class);
    }
}
```

**ポイント解説:**
- `#[Fillable([...])]`: Laravel 13から使える属性（Attribute）スタイルでの一括代入許可リスト。これまでの `protected $fillable = [...]` と同じ役割だが、すでに`User`モデルで使われている書き方に合わせて統一した
- `belongsTo(User::class)`: 「1人のmemberは1人のuserに属する」という多対1のリレーション定義

### phpunit.xml の修正（テスト環境を強制する）

```xml
<server name="APP_ENV" value="testing"/>
<env name="APP_ENV" value="testing" force="true"/>
```

**ポイント解説:**
- `<server>`タグ: PHPUnitの内部処理で `$_SERVER['APP_ENV']` を**無条件で**上書きする
- `<env>`タグ: `$_ENV` と `putenv()` を上書きする（`force="true"`をつけても`$_SERVER`には影響しない）
- 2つを併記することで、Laravelがどちらの置き場所を見ても`testing`が読めるようにした

---

## なぜそう書くか（設計の理由）

- **`<server>`タグを追加した理由**: docker-compose.ymlに `environment: APP_ENV=${APP_ENV:-local}` という設定があり、コンテナ起動時に`$_SERVER['APP_ENV']`へ`local`が書き込まれていた。Laravelの`Env`クラスは環境変数を読むときに`$_SERVER`を最優先で参照する実装になっている。そのため、phpunit.xmlで`<env>`タグに`testing`を指定しても`$_SERVER`は書き換わらず、Laravelは結局`local`を読んでしまい、テスト中もCSRFチェックが有効なままPOSTが419で弾かれていた。`<server>`タグだけが`$_SERVER`を直接上書きできるため、これを追加することで根本解決できた

- **CIでは問題が起きなかった理由**: GitHub ActionsのUbuntu環境では`APP_ENV`がOSレベルで注入されないため、phpunit.xmlの`<env>`設定がそのまま有効になり、`testing`として実行されていた。「ローカルだけ失敗・CIは通る」という不一致が、原因を環境差に絞り込む大きな手がかりになった

- **デバッグの進め方**: 最初は「force="true"を付ければ直るはず」という推測で1回失敗したが、そこで諦めず`vendor/phpunit/phpunit`のソースコード（`PhpHandler.php`）を直接読みに行き、`<env>`の処理が`putenv`と`$_ENV`しか書き換えていないことをコードレベルで確認してから対策を打った。「推測ではなく、ソースコードという一次情報で確認する」という調べ方が再現性のある解決につながった

---

# クリーンアーキテクチャのValueObject（PHP enum）とDBのenumの役割分離

**日付**: 2026-06-08（同日追記）
**会話の概要**: Phase 1 全7テーブルのマイグレーションを完了させ、テスト・コミットまで終えた後、Task 5（クリーンアーキテクチャ骨格）に着手。最初のステップであるValueObjects（PHP enum）を作成する中で、「マイグレーションで既にenumを定義しているのに、なぜまた同じ選択肢をPHP側でも定義し直すのか」という疑問を深掘りした。

---

## 今日学んだ概念

### ValueObject（値オブジェクト）としてのPHP enum
- **何か**: `'family'`や`'pending'`のような「決まった選択肢の中の1つ」を表す値を、生の文字列ではなくPHPの型（`enum`）として表現したもの。クリーンアーキテクチャでは`app/Domain/ValueObjects/`に置く
- **なぜ必要か**: 生文字列（マジックストリング）をコード中に直書きすると、タイプミス（`'famly'`など）が実行時まで発見できない。また「この値はどこで使われているか」をコード検索で正確に追えない（同じ文字列が無関係な場所にもヒットしてしまう）。enumにすることで、書く瞬間にエディタが候補を出し、間違った値はそもそも書けなくなる
- **例え**: レストランの注文システム。ウェイターが紙に手書きで注文を書く（生文字列）と、読み間違い・書き間違いが起きる。タブレットのボタン（enum）なら、決まった5つのボタンしかないので、そもそも誤入力が起きようがない

### DBのenum制約とPHPのValueObject（enum）の二重ガードの意味
- **何か**: 同じ「選択肢の集合」を、マイグレーション（DBスキーマ）とPHP enum（ドメイン層）の二箇所で定義する設計
- **なぜ必要か**: 役割が異なるから。DBのenumは「最終防衛ライン」＝不正な値が**保存されること自体**を防ぐ仕組み（インフラ層の制約）。PHPのValueObject（enum）は「最初の関門」＝アプリのコードを**書く時点**で間違った値を扱えなくする道具（ドメイン層の型）。両方あることで「書く瞬間に防ぐ」と「保存される瞬間に防ぐ」の二重チェックになる
- **例え**: 同じ厨房の例で言うと、DBのenumは「厨房の壁に貼られた『この5品目しか作れません』という張り紙」（最後の砦）、PHP enumは「ウェイターが使う、5つのボタンしかない注文タブレット」（そもそも変な注文が入らない仕組み）

### クリーンアーキテクチャの「Domain層はフレームワークに依存しない」原則とValueObjectの関係
- **何か**: CLAUDE.mdに明記されている原則「`app/Domain/` はビジネスルール。Laravelに依存しない」。ValueObject（PHP enum）はEloquentやLaravelの機能を一切使わない「素のPHP」なので、この原則を満たしたままドメイン層に置ける
- **なぜ必要か**: もしValueObjectを作らず、UseCase層が直接`'family'`という生文字列（＝Eloquentのenumカラムに保存される値とまったく同じ表現）を扱うと、「DBがどう値を保存するか」という**インフラ層の都合**が、ビジネスロジックを表現する**ドメイン層**にそのまま漏れ出してしまう。ValueObjectを挟むことで、「DB上の表現」と「ビジネス上の概念」が分離され、依存の方向（外側→内側）が崩れずに済む
- **例え**: 会社の各部署が「社内共通の用語集（ValueObject）」を持たず、それぞれ現場の伝票の書き方（DBの生文字列）をそのまま会議資料に転記しているような状態を想像する。伝票のフォーマットが変わるたびに、関係ない会議資料まで全部書き直しになってしまう。共通の用語集を間に挟んでおけば、伝票側が変わっても用語集の対応表だけ直せばよい

---

## 書いたコード

### ValueObject（PHP enum）4本

```php
<?php

namespace App\Domain\ValueObjects;

enum MemberType: string
{
    case Family         = 'family';
    case CramSchool     = 'cram_school';
    case Circle         = 'circle';
    case PublicFacility = 'public_facility';
    case Other          = 'other';
}
```

```php
<?php

namespace App\Domain\ValueObjects;

enum ProviderType: string
{
    case OverseasSchool = 'overseas_school';
    case LocalJapanese  = 'local_japanese';
}
```

```php
<?php

namespace App\Domain\ValueObjects;

enum PartnerStatus: string
{
    case Pending   = 'pending';
    case Approved  = 'approved';
    case Suspended = 'suspended';
    case Rejected  = 'rejected';
}
```

```php
<?php

namespace App\Domain\ValueObjects;

enum ThemeType: string
{
    case Culture = 'culture';   // 文化交流
    case English = 'english';   // 英語学習
    case Global  = 'global';    // 国際理解
}
```

**ポイント解説:**
- `enum MemberType: string`: PHP 8.1から使える「バックド enum（backed enum）」。`: string`を付けることで、各caseに文字列値（`'family'`など）を紐付けられる。これによりDBに保存されている`'family'`という値と、コード上の`MemberType::Family`を相互変換できる
- `namespace App\Domain\ValueObjects;`: クリーンアーキテクチャのディレクトリ構成で「ドメイン層の値オブジェクト」を置く場所。Laravel固有のクラス（`Illuminate\...`）への`use`が一切無いことが、「フレームワーク非依存」を体現している

---

## なぜそう書くか（設計の理由）

- **マイグレーションのenumとPHPのenumを両方定義する判断**: 「二重定義で面倒」に見えるが、これは「DRY原則違反」ではなく「レイヤーごとに役割が異なる別概念」と捉えるのが正しい。DB側は「保存時の制約」、PHP側は「コードを書く時・実行する時の型」。クリーンアーキテクチャでは、こうした「同じ意味を持つが層によって表現形式が異なるもの」を変換する境界（ValueObject、Repository実装など）を意図的に作ることで、各層の独立性を保つ
- **ハンズオンで自分の手で書いた理由**: 設計判断を理屈で理解するだけでなく、実際に「namespace」「enum構文」「ファイル配置場所」を手で書くことで、クリーンアーキテクチャの「層」が単なる概念ではなく、ディレクトリとnamespaceという物理的な境界として表現されることを体感できる

# Repository Interfaceと依存性注入（DI）の流れ

**日付**: 2026-06-08（同日追記）
**会話の概要**: Task 5-2でRepository Interface（`MemberRepositoryInterface`/`PartnerRepositoryInterface`）を作成。「このInterfaceは何のためにあり、どのファイルで・どんな順番で使われるのか」を時系列で深掘りした。

---

## 今日学んだ概念

### Repository Interface（リポジトリのインターフェース）
- **何か**: 「データの保存・取得はこういう形でできますよ」という**約束事だけ**を定義したPHPの`interface`。実際の処理（DB操作）は書かない
- **なぜ必要か**: クリーンアーキテクチャは「依存の方向は外側→内側のみ」が原則。しかしUseCase（内側）は「会員を保存する」処理を必要とする。もし直接`Member::create()`（Eloquent＝外側の技術）を呼んでしまうと、内側が外側に依存することになり原則が崩れる。そこでInterface（契約書）を内側（Domain層）に置き、UseCaseは「契約書」だけを知っていればよい状態を作る。実際の実装（Eloquent版）は外側（Infrastructure層）に置き、その契約書を「実装する」形にすることで、依存の矢印を逆転させる（**依存性逆転の原則 / DIP**）
- **例え**: レストランのホール係（UseCase）は「厨房に渡す注文票のフォーマット（Interface）」だけ知っていればよく、厨房の中身（Eloquent実装）がどうなっているかを知る必要がない。厨房の設備を入れ替えても、ホール係の仕事のやり方は変わらない

### 依存性注入（DI）とサービスコンテナによる自動解決
- **何か**: クラスが必要とする部品（依存）を、自分で`new`して用意するのではなく、外部（Laravelのサービスコンテナ）から「注入してもらう」仕組み
- **なぜ必要か**: UseCaseのコンストラクタが`MemberRepositoryInterface`という型を要求するだけで、Laravelが自動的に「事前に登録しておいた実装（`EloquentMemberRepository`）」を生成して渡してくれる。これにより、UseCaseのコード中に具体的な実装クラス名（`EloquentMemberRepository`）が一切登場しない＝コードの上でも「内側は外側を知らない」が実現される
- **例え**: 開店前に店長（`AppServiceProvider`）が「注文が来たらこの厨房チームに回す」と裏で決めておく。営業中、ホール係（UseCase）はただ注文票を書くだけで、実際にどの厨房チームが調理しているかを意識しない。店長が裏で結びつけている

---

## 書いたコード

### Repository Interface（契約書）

```php
<?php

namespace App\Domain\Repositories;

use App\Models\Member;

interface MemberRepositoryInterface
{
    public function create(array $attributes): Member;
}
```

**ポイント解説:**
- `interface`: 処理の中身を持たず、「このメソッドが存在し、こういう型を受け取り・返す」という形だけを宣言する。実装クラス（`EloquentMemberRepository`）は`implements`してこの形を満たす義務を負う
- `public function create(array $attributes): Member;`: 「属性の配列を渡せば`Member`オブジェクトを返す保存処理を提供する」という1つの約束のみ。これを見ればUseCase側は「中身がEloquentだろうがモックだろうが、これを呼べばMemberが手に入る」と信頼してコードを書ける
- `use App\Models\Member;`: 戻り値の型として`Member`（Eloquentモデル）を参照しているが、これは「Domain層がInfrastructure層に依存している」という違反ではなく、「ドメインが扱うデータの形」を表現するための参照として許容される設計判断（CLAUDE.mdの設計方針に準拠）

---

## なぜそう書くか（設計の理由）

- **Interfaceをどこにどう使うか、3点セットで理解する**: ①`RegisterMemberUseCase`のコンストラクタで型として受け取る側、②`EloquentMemberRepository`で`implements`して中身を実装する側、③`AppServiceProvider`で「Interfaceが要求されたらこの実装を渡す」と紐付ける側。この3つが揃って初めて「UseCaseがInterfaceに依存するだけで、実行時には自動的にEloquent実装が渡ってくる」という流れが成立する。1つだけ見ても全体像はつかめず、3点を時系列（起動前の準備→リクエスト時→実処理）で追うことで初めて納得できた
- **「UseCaseのコードに実装クラス名が一切出てこない」ことの価値**: これが「内側が外側に依存しない」を**コードレベルで体現している**証拠。将来DBやORMを乗り換える事態になっても、UseCase層は1行も変更せずに済み、Infrastructure層の実装とAppServiceProviderの紐付けだけ差し替えればよい

---

# UseCaseとInput/Output（DTO）—「業務手順」をコードにする

**日付**: 2026-06-08（同日追記）
**会話の概要**: Task 5-3で`RegisterMemberInput`/`RegisterMemberOutput`/`RegisterMemberUseCase`の3点セットを作成。それぞれが何をしているのか、なぜControllerに直接書かずわざわざ分けるのかを深掘りした。

---

## 今日学んだ概念

### Input/Output（DTO: Data Transfer Object）と`readonly class`
- **何か**: UseCaseへの「入力」と「出力」を、Laravel固有の型（`Request`や`Eloquentモデル`そのもの）ではなく、素のPHPオブジェクトとして包んだもの。`readonly class`はPHP 8.2の機能で、一度プロパティに値を入れたら後から書き換え不可（イミュータブル＝不変）にできる
- **なぜ必要か**: ControllerはLaravelの`Request`を持っているが、そのままUseCaseに渡すとUseCaseがLaravelに依存してしまいクリーンアーキ原則が崩れる。Controllerが`Request`から必要な値だけ取り出し`Input`に詰め替えることで、UseCaseは「Laravelの`Request`を一切知らない素のPHPオブジェクト」だけを相手にできる。`readonly`にするのは「届いた入力データ・返ってきた結果が途中で勝手に書き換わらない」という安全性を型で保証するため
- **例え**: 注文を厨房に伝える時、紙の伝票（`readonly`なInput）に書いて渡せば、厨房に届いた後で誰かが内容を書き換える心配がない。料理が出来上がった時も、そのまま手渡しせず「お盆（Output）」に乗せて運ぶ。お盆なら、後で取り皿やナプキンを追加しても渡し方自体は変わらない

### UseCaseは「業務手順そのもの」をコードにしたもの
- **何か**: `RegisterMemberUseCase::execute()`は「①認証用Userアカウントを作る→②会員プロフィール（Member）を紐付けて作る→③結果を返す」という、**会員登録という業務の手順**をそのままコードにしたもの
- **なぜ必要か**: もしこの手順をControllerに直接書くと、「HTTPリクエストの受付」と「会員登録という業務知識」が1つのメソッドに混ざってしまう。すると（a）「会員登録」だけを取り出してテストできない（常にHTTPリクエストが必要になる）、（b）将来、管理画面やバッチ処理から同じ「会員登録」をしたくなった時にコードを複製するしかない、という問題が起きる。UseCaseとして独立させることで「会員登録とは何か」という業務知識が1箇所に閉じ込められ、HTTPの詳細ともDBの実装詳細(Eloquent)とも切り離されたまま、どこからでも安全に呼び出せる
- **例え**: レシピカード（UseCase）に「①生地を作る→②具材を乗せる→③焼く」と手順だけ書いておけば、家庭のオーブンでも、店の業務用オーブンでも（＝Controllerが違っても）同じ手順で同じ料理が作れる。レシピカードに「オーブンの操作パネルの押し方」まで書いてしまうと、オーブンが変わるたびにレシピを書き直すことになる

## 書いたコード

### Input（UseCaseへの入力を詰める「荷物」）

```php
readonly class RegisterMemberInput
{
    public function __construct(
        public string $email,
        public string $password,
        public string $name,
        public string $type,           // MemberType値
        public ?string $orgName,
        public string $prefecture,
        public string $contactName,
        public ?string $gradeRange,
    ) {}
}
```

### Output（UseCaseからの戻り値を詰める「荷物」）

```php
readonly class RegisterMemberOutput
{
    public function __construct(
        public User $user,
    ) {}
}
```

### UseCase本体（「会員登録」という業務手順）

```php
class RegisterMemberUseCase
{
    public function __construct(
        private MemberRepositoryInterface $memberRepository,
    ) {}

    public function execute(RegisterMemberInput $input): RegisterMemberOutput
    {
        // ① 認証用のUserアカウントを作る（role='member'で）
        $user = User::create([
            'name'     => $input->name,
            'email'    => $input->email,
            'password' => Hash::make($input->password),
            'role'     => 'member',
        ]);

        // ② そのUserに紐づく「会員プロフィール」をMemberとして作る
        $this->memberRepository->create([
            'user_id'      => $user->id,
            'type'         => $input->type,
            'org_name'     => $input->orgName,
            'prefecture'   => $input->prefecture,
            'contact_name' => $input->contactName,
            'grade_range'  => $input->gradeRange,
        ]);

        // ③ 結果を荷物に詰めて返す
        return new RegisterMemberOutput($user);
    }
}
```

**ポイント解説:**
- `public string $email` のように全プロパティを`public`にしているのは、外から自由に値を**読める**ようにしつつ、書き込みはコンストラクタ時のみ（＝読み取り専用のデータの入れ物）にする設計パターン
- `?string $orgName`: `?`は「nullを許容する」という意味。設計書でも「家庭利用者は`org_name`がnull」とされており、その業務ルールが型にそのまま表れている
- `private MemberRepositoryInterface $memberRepository`: コンストラクタの引数に直接`private`を付けると、自動的にプロパティとして保存される（コンストラクタプロモーション）。Eloquentの実装クラス名は一切登場しない

---

## なぜそう書くか（設計の理由）

- **戻り値を`User`そのものではなく`Output`で包む理由**: 将来「登録直後に発行する認証トークンも一緒に返したい」のように戻り値の構造が増えても、`Output`クラスにプロパティを追加するだけで済み、呼び出し側のコード（`$output->user`）は壊れない。また型を見ただけで「このUseCaseが何を返す処理なのか」が一目で分かる
- **`execute()`という1つのメソッドに業務手順を凝縮する理由**: 読んだ瞬間に「会員登録とは、ユーザー作成→会員プロフィール作成→結果を返す、という2段階の手順である」という業務知識がそのまま読み取れる。HTTPの詳細(Controller)にもDBの実装詳細(Eloquent)にも汚されていない、「ビジネスルールの core」がここにある
