## 今日学んだ概念

### 設定の外部化（config × env）
- **何か**: 鍵やURLなど「環境ごとに変わる値」をコードに直書きせず、`.env`（実値）→ `config/*.php`（`env()` で参照）→ アプリ本体（`config('services.stripe.secret')` で参照）の3段で扱う仕組み。
- **なぜ必要か**: 本番・テスト・各開発者で値が違う。コードに鍵を書くと Git に秘密が漏れる。設定を1か所（`config`）に集約するとアプリ本体は「どこから来た値か」を気にせず使える。
- **例え**: `.env` は「各家庭の電圧（国ごとに違う）」、`config` は「コンセントの規格を揃える変換アダプタ」。家電（アプリ本体）はアダプタ越しにつなぐだけで動く。

### Stripe Checkout（リダイレクト方式）
- **何か**: 自前でカード番号を扱わず、Stripe がホストする決済ページに**リダイレクト**して支払わせ、完了後にアプリへ戻す決済方式。確定通知は Webhook で受ける。
- **なぜ必要か**: カード情報を自社サーバに通さない＝PCI準拠の負担が激減。今回の設計では「決済・確定は participant 単位」で、予約時に枠(draft)＋参加者(pending)を作り、Webhook で両者を確定する。
- **例え**: 決済だけ「警備の厳重な別室（Stripe）」に任せ、終わったら受付（アプリ）に「確定したよ」と内線（Webhook）が入る。

### スロット管理の2テーブル設計
- **週次パターン** `partner_schedules`: 「毎週○曜の○時から」という繰り返しルール。
- **例外ブロック** `partner_schedule_blocks`: 「この日は休み」という単発の打ち消し。
- **なぜ2つに分けるか**: 毎週の規則は少数行で表現でき、休みは「例外」として別管理する方が、全日付を1行ずつ持つより圧倒的に省データ。実際の予約可能枠は SlotService が「週次パターン − ブロック日」で動的計算する（Task 4 で実装予定）。

## 書いたコード

### config/services.php に Stripe 設定を追加

```php
'stripe' => [
    'key'            => env('STRIPE_KEY'),
    'secret'         => env('STRIPE_SECRET'),
    'webhook_secret' => env('STRIPE_WEBHOOK_SECRET'),
],
```

**ポイント解説:**
- `env('STRIPE_KEY')`: ここでだけ `env()` を呼ぶ。アプリ本体では `config('services.stripe.key')` を使う（`config:cache` した本番で `env()` が null を返す事故を防ぐため）。
- 3キーの役割: `key`=公開可能キー(pk_)、`secret`=サーバ専用シークレット(sk_)、`webhook_secret`=Webhook署名検証用(whsec_)。

### partner_schedules マイグレーション

```php
Schema::create('partner_schedules', function (Blueprint $table) {
    $table->id();
    $table->foreignId('partner_id')->constrained()->cascadeOnDelete();
    $table->unsignedTinyInteger('day_of_week'); // 0=月 … 6=日（JST基準）
    $table->time('start_time_jst');             // 例 "10:00:00"
    $table->unsignedInteger('duration_min');    // 45 or 60
    $table->unsignedInteger('max_sessions')->default(1);
    $table->timestamps();
});
```

**ポイント解説:**
- `foreignId('partner_id')->constrained()->cascadeOnDelete()`: `partners.id` への外部キー。パートナー削除時にスケジュールも一緒に消える（孤児レコードを残さない）。
- `unsignedTinyInteger('day_of_week')`: 曜日は 0〜6 の小さい整数。1バイトで足りるので `tinyInteger`。負値はないので `unsigned`。
- `time('start_time_jst')`: 日付なしの時刻だけ。列名に `_jst` を付けて「JST基準」を明示（タイムゾーン取り違え事故の予防）。

### partner_schedule_blocks マイグレーション

```php
Schema::create('partner_schedule_blocks', function (Blueprint $table) {
    $table->id();
    $table->foreignId('partner_id')->constrained()->cascadeOnDelete();
    $table->date('blocked_date');
    $table->string('reason')->nullable();
    $table->timestamps();

    $table->unique(['partner_id', 'blocked_date']); // 同日重複ブロック禁止
});
```

**ポイント解説:**
- `unique(['partner_id', 'blocked_date'])`: **複合ユニーク制約**。同じパートナーが同じ日を2回ブロックできない。アプリ側のチェック漏れがあっても DB が最後の砦として弾く。

## なぜそう書くか（設計の理由）

- **`.env` はコミットせず `.env.example` だけコミット**: `.env` は秘密の実値（Git無視）、`.env.example` は「このキーが必要」を示す値なしテンプレ。新メンバーは example をコピーして自分の値を入れる。CLAUDE.md でも「新env追加時は必ず example も更新」と規約化されている。
- **曜日を文字列でなく整数 0〜6 で持つ**: 比較・並べ替え・計算（「今日が水曜なら…」）が速く・正確。表示時に「月火水…」へ変換するのは表示層の責務。
- **日付を全部持たず週次＋例外に分ける**: 正規化の発想。「繰り返しルール」と「例外」を分離すると、ルール変更が1行で済む。

## 躓きポイント深掘り

今日はセットアップ中心で大きな詰まりはなし。代わりに「なぜ env を config 経由で使うのか」を1点だけ深掘りする。

### なぜアプリ本体で env() を直接呼ばないのか

- **何に気をつけたか**: `config/services.php` の中だけで `env()` を使い、コントローラ等では `config()` を使うルール。
- **根本の仕組み**: 本番で高速化のため `php artisan config:cache` を実行すると、全 config がキャッシュされ、その後 `env()` は **null を返すようになる**（.env を読まなくなる）。config 経由なら値はキャッシュに焼かれているので無事。env を直接呼んでいた箇所だけ本番で壊れる、という発見しづらいバグになる。
- **関連技術マップ**:
  - **config:cache**: 設定ファイル群を1つにまとめて高速化する本番向けコマンド。これが env 直読みを壊す張本人。
  - **12-Factor App の "Config"**: 設定を環境変数に逃がす設計思想。今回の3段構成の背景。
  - **Webhook署名検証**: `webhook_secret` は Task 10 で「Stripeからの通知が本物か」を検証するのに使う。今は空でも進める。
- **理解チェック**: 「本番でだけ Stripe の鍵が null になった」原因の典型は？ → コントローラで `env('STRIPE_SECRET')` を直接呼んでいて、`config:cache` 後に env が読まれなくなったから。

# 【同日追記 Task 3】Eloquentモデルとリレーション、phpstan並列ワーカーの罠

**会話の概要**: Task 2 のテーブルに対応する Eloquent モデル2つ（`PartnerSchedule`/`PartnerScheduleBlock`）を作り、`Partner` にリレーションを追加。phpstan の並列ワーカーが落ちる現象を `--debug` で切り分けた。

## 今日学んだ概念（Task 3）

### Eloquent のリレーション（BelongsTo / HasMany）
- **何か**: テーブル間の「親子・所属」を、SQLのJOINを書かずに `$partner->schedules` のようなプロパティで辿れるようにする仕組み。
- **2方向で対になる**: 子→親は `belongsTo`（`PartnerSchedule` は1つの `Partner` に属す）、親→子は `hasMany`（1人の `Partner` は複数の `schedule` を持つ）。Task 2 で張った外部キー `partner_id` がこの対応の土台。
- **例え**: `belongsTo` =「この生徒はどのクラスに属す？」、`hasMany` =「このクラスにいる生徒全員」。同じ関係を逆から見ているだけ。

### リレーションの戻り型注釈（`: HasMany`）
- **何か**: メソッドの戻り値の型を `public function schedules(): HasMany` と明示すること。
- **なぜ必要か**: 動作には不要（書かなくても動く）。だが付けると IDE補完・larastan の型追跡が確実になる。核心まとめ §3「リレーションは戻り型を書く」の実践。

## 書いたコード（Task 3）

```php
// PartnerSchedule.php（子→親）
public function partner(): BelongsTo
{
    return $this->belongsTo(Partner::class);
}

// Partner.php（親→子。既存 sessions() に追加）
public function schedules(): HasMany
{
    return $this->hasMany(PartnerSchedule::class);
}
```

**ポイント解説:**
- `#[Fillable([...])]`: Laravel 13 の**属性(Attribute)記法**。旧来の `protected $fillable = [...]` と同じ「複数代入を許可する列の許可リスト」を、クラス宣言の上に書く新スタイル。既存モデルもこの形で統一されていたので合わせた。
- `$casts` で `'blocked_date' => 'date'`: DBから来る文字列を Carbon の日付オブジェクトに自動変換。日付計算（SlotService）で効いてくる。

## なぜそう書くか（設計の理由・Task 3）

- **既存の `user()`/`sessions()` は戻り型なし、新規だけ戻り型あり、の不統一を許容した**: 理由は「歴史的経緯」。既存は Phase 1 で省略して書かれた。今回は付ける方針。**統一するなら既存にも付けるのが理想**だが、今回は「既存改変を混ぜるとコミットの意図がぼやける」を優先し、追加分のみ注釈付きでコミットした。＝**スコープを絞る判断**。

## 躓きポイント深掘り（Task 3）

### phpstan が `Child process error (exit code 255)` で止まる

- **何に躓いたか**: `phpstan analyse app/Models/` を普通に実行したら `[ERROR] Found 1 error / Child process error (exit code 255) while running parallel worker` とだけ出て、**どのコードが悪いのか一切わからない**。
- **根本の仕組み**: phpstan は高速化のため**複数の子プロセス（並列ワーカー）に解析を分担**させる。この**ワーカー自身**が Docker コンテナのメモリ/プロセス制約で異常終了(255)すると、「コードのエラー」ではなく「ワーカーが死んだ」という**インフラ層のエラー**が表に出る。コードの良し悪しとは無関係。
- **切り分け方**: `--debug` フラグを付けると**並列を無効化**し、1プロセスで順に解析する → ワーカー問題が消え、**真の結果（今回は `No errors`）**が見える。「ツールが吐くエラー = コードのエラー」とは限らない、を体感した。
- **恒久対策（任意）**: `phpstan.neon` に `parallel: maximumNumberOfProcesses: 2` でワーカー数を絞ると安定する。
- **関連技術マップ**:
  - **並列処理 / ワーカープロセス**: 仕事を複数プロセスに分けて速くする一般技法。速いが、ワーカー1つの死が全体エラーに化ける弱点。
  - **exit code**: プロセス終了時の番号。0=成功、それ以外=異常。255 は「捕捉されない致命的終了」の典型で、原因が一意に定まらない曖昧なコード。
  - **larastan**: phpstan の Laravel 拡張。今回のように Model 解析もこれが担う（→ 2026-06-24 ノート）。
- **理解チェック**: 静的解析が「Child process error 255」しか出さず原因不明なとき、まず何を試す？ → `--debug`（並列オフ）で再実行し、コード由来か環境（ワーカー）由来かを切り分ける。
